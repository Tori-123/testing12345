# 1.1 命题发散：国际象棋训练平台 · 10 个微观痛点

原始命题：运用目前市面上的国际象棋 API，打造出一个国际象棋训练平台，用来帮助棋手训练。

约束：场景必须垂直；训练平台不能做成「又一个能下棋的网站」。棋力计算交给现成国际象棋 API（chess-api.com / Lichess / Maia / tablebase），大模型只做「把引擎结果翻译成可执行的人话」这一层。

---

## 场景一：复盘时只看到 +1.4，完全不知道自己错在哪

- **Problem Statement (痛点界定)**  
  业余棋手下完一盘，打开分析，看到的是 `eval: +1.42`、`pv: Nxe5 Bxe5...`。他们能看懂「这步不好」，看不懂「这步坏在丢掉了哪个具体机会」：是漏了捉双、把王走去危险格，还是主动把好马兑成坏象。痛点不是「没有分析」，而是「分析不是人话」。

- **为什么传统方案失效**  
  没有大模型时，引擎只会吐 UCI 着法和百分兵。Lichess/Chess.com 的彩条能告诉你「这里掉分了」，但不会用一句中文说出因果。棋手要么请私教逐着讲，要么自己啃英语注释，复盘常常停在「哦，原来该走马」就结束。

- **产品方向脑暴（What to Build）**  
  粘贴 PGN 或走完一盘 → 调 chess-api.com / Lichess 拿到每步评估差 → 只把「评估骤降」的 1–3 个局面 + 候选着交给大模型，输出三句话：错在哪、正确计划是什么、下次出现同类形状先看哪条线索。

- **黑客松 MVP 匹配度**  
  36 小时只做单屏：输入 PGN → 高亮最差一步 → 右侧一段中文讲解。引擎算力用 `POST chess-api.com/v1`；大模型只用「解释这一个局面」这一种能力。

- **MCP / RAG 必要性**  
  - MCP：不必要。一次请求、一个引擎、一个模型，硬编码 HTTP 即可。  
  - RAG：不必要。讲解基于当前 FEN 与引擎变化，不需要检索名局库。

---

## 场景二：陪练要么碾压你，要么下得完全不像人

- **Problem Statement (痛点界定)**  
  1200–1600 的棋手想「找个水平接近的对手练手」。Stockfish 即使用低 depth，仍会下出人类几乎不下的冷门着；Lichess 人机又经常重复同一套开局。他们缺的不是更强的引擎，而是「会犯错、棋风像同级人类」的固定陪练。

- **为什么传统方案失效**  
  传统引擎的优化目标是胜率，不是像人。降低 depth / Skill Level 只会让它「算得浅」，不会让它「像 1500 那样漏一步再顽强」。没有大模型时，也没人在对局中用自然语言告诉你「这一步开始，你的对手在模仿业余棋手的常见偏见」。

- **产品方向脑暴（What to Build）**  
  用 Lichess 挑战 Maia（`maia1/5/9`）或本地 Maia 当对手；每步把局面发给大模型，用一句话点评「这是同级人类会下的着，还是你刚走出了引擎着」。不自研棋力。

- **黑客松 MVP 匹配度**  
  若不想接 Lichess OAuth，退化为：chess-api.com 出棋 + 大模型只负责赛后用「人类常见失误框架」点评用户着法。完整 Maia 对局可列为加分项，不是 36 小时必做。

- **MCP / RAG 必要性**  
  - MCP：低必要。只有同时接「出棋引擎 + 平台对局」两个工具时才值得做成 MCP；黑客松直接写两个 fetch。  
  - RAG：不必要。Maia 本身就是「人类着法模型」，不必再检索棋谱。

---

## 场景三：一盘 40 步，不知道哪 2 步才真正丢了

- **Problem Statement (痛点界定)**  
  棋手复盘时面对整盘逐步评估，认知过载。他们真正需要的是教练会做的事：指出「第 18 步漏杀是败着，第 31 步只是残局技术问题」。痛点是「关键失误定位」，不是「全盘分析」。

- **为什么传统方案失效**  
  引擎可以给每步 centipawn loss，但阈值、归类（战术失误 / 战略漂移 / 时间慌乱）需要人。没有大模型，软件只能画红绿条，用户仍要把 40 个数字自己聚类。

- **产品方向脑暴（What to Build）**  
  对每步调引擎评估，算出评估跳变；用简单规则筛出 Top 2 跳变点；大模型只对这两个局面做「败着 / 不精确」分类，并给一句「如果重来，先检查什么」。

- **黑客松 MVP 匹配度**  
  核心能力是「比较前后两步的 eval 差」。chess-api.com 或 Lichess cloud-eval（开局）都能用。大模型做分类与措辞，不做搜棋。单屏列表：两张棋盘截图 + 两段话。

- **MCP / RAG 必要性**  
  - MCP：不必要。  
  - RAG：不必要。分类规则可以写死在 prompt 里（跳变 >1.5 兵 = 败着）。

---

## 场景四：同一类挂子反复发生，平台却还在让你「再下一盘」

- **Problem Statement (痛点界定)**  
  很多业余棋手的主问题不是开局理论，而是「没看被吃的棋」。他们在 Lichess 下了 200 盘，平台仍按积分匹配，不会说「你这周 7 次丢掉未保护的马，今晚只练这个」。痛点是训练没有针对个人漏洞的闭环。

- **为什么传统方案失效**  
  没有大模型时，要从 PGN 里识别「未保护棋子被吃」需要写死规则引擎，还要把漏洞翻译成可练的题。现成谜题库按主题打标签，对不上「你自己的那几盘」。

- **产品方向脑暴（What to Build）**  
  导入最近几盘 PGN → 引擎标出吃子失误 → 大模型把失误归成一个中文标签（如「无根马」）→ 从该盘抽出一个局面，让用户重下这一手。API 给出正解，大模型只解释标签。

- **黑客松 MVP 匹配度**  
  36 小时不要做用户系统和历史数据库。演示路径：粘贴 1 盘 PGN → 找出 1 个挂子局面 → 让用户重下。chess-api.com 判断正误。

- **MCP / RAG 必要性**  
  - MCP：不必要。  
  - RAG：低必要。不要自建题库检索；就用用户自己的那一盘当题目。自建 RAG 谜题库是 36 小时陷阱。

---

## 场景五：开局走完书本变例后，完全没有计划

- **Problem Statement (痛点界定)**  
  棋手能背「意大利开局走 Bc4」，走完 8 步就停转。引擎会继续给最佳着，但不会说「白方计划是打 d 兵、黑方要及时 c6」。痛点是「开局计划缺失」，不是「开局数据库不够大」。

- **为什么传统方案失效**  
  Lichess Opening Explorer 能给出着法胜率，但统计不是计划。开局书是长文本，临场来不及读。没有大模型，无法把「当前 FEN + 探索器着法」压成两句可执行的计划。

- **产品方向脑暴（What to Build）**  
  用户走开局 → 调 `explorer.lichess.ovh` 拿主流续着 → 把当前 FEN、最常见 3 着、chess-api.com 评估一并交给大模型，只输出：双方计划各一句、下一步优先观察哪个格子。

- **黑客松 MVP 匹配度**  
  大模型能力限定为「摘要计划」。数据来自 Lichess explorer（公开 HTTP）+ 一次引擎评估。不要做完整开局树 UI。

- **MCP / RAG 必要性**  
  - MCP：低必要。explorer + 引擎两个 HTTP，直接串即可；做成 MCP 对黑客松无增益。  
  - RAG：不必要。Explorer 已经是检索；再对开局书做 RAG 会引入语料清洗，36 小时极易翻车。

---

## 场景六：战术题做对了，却讲不出「这是在利用什么」

- **Problem Statement (痛点界定)**  
  棋手刷 Lichess Puzzle，点对了就下一题。他们需要的是一句「这是过载：你的后同时盯着被牵的马和底线」。痛点是「有答案无概念」，导致换个外形就不会。

- **为什么传统方案失效**  
  谜题平台有主题标签（fork / pin），但是英文标签加棋盘，不等于理解。没有大模型，无法针对「这一题的这一个关键格」生成中文概念讲解。

- **产品方向脑暴（What to Build）**  
  用 Lichess 公开谜题数据（或预置 20 道静态谜题）→ 用户作答 → 对则用大模型用主题词讲解；错则把引擎正解和用户着法对比，说明差在哪条战术动机。

- **黑客松 MVP 匹配度**  
  不要接 Lichess 账号同步。预置 JSON 谜题 + chess-api.com 验证 + 大模型讲解，是最稳的 36 小时回路。Lichess puzzle API/数据下载可作为加分。

- **MCP / RAG 必要性**  
  - MCP：不必要。  
  - RAG：不必要。主题词表很小，写进 prompt（牵制、捉双、过载、闪将）比向量库更稳。

---

## 场景七：残局「理论能赢」，对着引擎却兑不掉

- **Problem Statement (痛点界定)**  
  业余棋手残局经常把赢势下成和棋。他们知道「王兵残局该用对王」，但面对具体局面不会选格子。普通人机不会只练这一种残局，也不会在你走错时说「你把王走到了短边，关键格丢了」。

- **为什么传统方案失效**  
  7 子以内 Lichess tablebase 能给完美着法，但输出仍是着法列表。没有大模型，用户看不到「关键格 / 对王 / 正方形法则」这些可迁移概念。自己写残局教练规则工作量极大。

- **产品方向脑暴（What to Build）**  
  只做一个残局课：王兵对王。tablebase 出最佳着与胜和判定；用户走错时，大模型用事先规定的术语解释为什么这步把赢势变成和棋。

- **黑客松 MVP 匹配度**  
  范围锁死一种残局。`https://tablebase.lichess.ovh/standard?fen=` 提供胜负；大模型只做法则讲解。不要做 7 子任意残局。

- **MCP / RAG 必要性**  
  - MCP：不必要。  
  - RAG：不必要。残局法则就几条，放进 system prompt。

---

## 场景八：对手走出冷门开局，当场不知道对方想干什么

- **Problem Statement (痛点界定)**  
  对局第 4 步遇到少见着（例如偏门侧翼弃兵），棋手大脑空白。他们需要 10 秒内的「意图翻译」：对方在抢哪个格子、常见惩罚是什么，而不是一篇开局百科。

- **为什么传统方案失效**  
  临场不能翻书。Explorer 能告诉你这步胜率低，但不解释意图。引擎会给最佳惩罚着，但不说明「为什么这是惩罚」。时间压力下，原始 API 输出无法被人类瞬时消化。

- **产品方向脑暴（What to Build）**  
  训练模式（非作弊线上对局）：用户输入当前 FEN 或走子序列 → explorer 查出现频率 → 引擎给最佳应对 → 大模型输出限 40 字的意图 + 一条应对原则。产品定位是赛后/训练助手，避免做成线上作弊器。

- **黑客松 MVP 匹配度**  
  明确写成「训练室里问意图」，不要做实时外挂。单次 FEN → 三行字。chess-api.com + explorer 足够。

- **MCP / RAG 必要性**  
  - MCP：不必要。  
  - RAG：不必要。用 explorer 的频率当「冷门」信号即可，不必检索维基。

---

## 场景九：教练不在时，想问「这步能不能走」却得不到能教人的回答

- **Problem Statement (痛点界定)**  
  自学棋手盯着一个自己想走的着（例如「我想冲 e5」），引擎要么说不是最佳，要么列出 5 条 PV。他们需要的是像教练那样：允许/警告 + 理由 + 「什么条件下这步才成立」。痛点是「候选着咨询」，不是「让 AI 替我下棋」。

- **为什么传统方案失效**  
  引擎的 MultiPV 能比较几步的分数，但不会处理自然语言问题「能不能冲兵」。没有大模型，用户无法用中文提问，也无法得到条件句式的回答。

- **产品方向脑暴（What to Build）**  
  棋盘选一步（或输入 SAN）→ chess-api.com 用 `searchmoves` 评估该着，再评估最佳着 → 大模型对比两个分数，回答：可以走 / 不建议，以及成立条件。

- **黑客松 MVP 匹配度**  
  大模型能力是「对比两个评估并说人话」。引擎 API 已支持限定搜索着。单屏：棋盘 + 输入框「我想走 ____」。

- **MCP / RAG 必要性**  
  - MCP：不必要。一个引擎 API 调两次。  
  - RAG：不必要。

---

## 场景十：训练完没有「下一盘只改一件事」的作业

- **Problem Statement (痛点界定)**  
  棋手刷完谜题或人机后，不知道明天该练什么。平台有数据，没有「一条可执行作业」。痛点是训练结束时缺少教练式布置：今晚只记住一件事。

- **为什么传统方案失效**  
  没有大模型时，作业要么是固定课程表（与个人无关），要么是统计报表（用户不会自己翻译成行动）。把「本盘最严重的一类失误」写成一句作业，需要语言层，不是更多图表。

- **产品方向脑暴（What to Build）**  
  任何一盘训练结束：取 1 个最大评估跳变 → 大模型生成一条作业（例如「下一盘每次对方吃子前，先问这个子有没有保护」）+ 一个从本盘抽出的重下局面。不需要课程系统和排行榜。

- **黑客松 MVP 匹配度**  
  这是场景一/三的收口。36 小时不必独立做成产品模块，可作为复盘页底部的一句话。大模型只生成「一条作业」。

- **MCP / RAG 必要性**  
  - MCP：不必要。  
  - RAG：不必要。作业来自本盘，不检索历史用户。

---

## 给团队拍板用的收敛提示

更适合 36 小时、且能真正用上「国际象棋 API + 大模型」分工的，是下面三个（建议从中人工锁定 1 个再做 1.2）：

| 优先级 | 场景 | 原因 |
| --- | --- | --- |
| 最稳 | 场景一 / 三：关键失误人话复盘 | 单屏、单向数据流、API 已实测 |
| 很稳 | 场景六：战术题 + 概念讲解 | 可预置谜题，不怕引擎限流 |
| 有辨识度 | 场景九：询问「这步能不能走」 | 交互极简，和「又一个人机」差异大 |

高风险、建议本轮不要选：完整 Lichess OAuth 在线对局（场景二完整版）、自建 RAG 开局书、实时对局外挂式提示（合规与实现都重）。
