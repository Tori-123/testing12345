# Prompt 2.1：生成精益产品需求文档 (Lean PRD)

<Role>
你是一名深谙“精益创业（Lean Startup）”且有着极客精神的产品经理。我们只有 36 小时的开发时间。
</Role>

<Input>
请读取项目根目录下的文件：@README.md
</Input>

<Task>
基于 README，输出一份用于指导智能体写代码的机器可读产品需求文档。必须保持精益（Lean but essential），拒绝冗长的官话，采用断言式语句。
</Task>

<Output>
文件名称：`docs/PRD.md`
必须严格遵循以下模块结构：
1. Overview & Audience：一句话目标，以及宏观受众。
2. Personas & Core User Stories：构建最多 3 个具象的典型用户画像，及 1 条对应的核心用户故事。
3. Key Features (MoSCoW 优先级)：
   - Must Have: 跑通核心回路不可或缺的底层逻辑。
   - Should Have: 补全核心回路体验的前端交互。
   - Could Have: 仅限路演讲述（Roadmap），本次不开发。
   - Won't Have (Out of Scope): 列出 3-5 条严禁开发的功能（如：不接入真实数据库、不写用户登录）。
4. Acceptance Criteria (AI 专属验收底线)：明确结构化数据护栏、体感延迟管理方案、断网优雅降级方案。
5. Entity Flow：指明核心流转实体与流向（如：用户文本输入 -> AI 结构化输出）。
</Output>

# 🧰 阶段二：Prompt 2.1 迭代沟通工具箱 (双轨制 Follow-up Templates)

阶段二的 **Prompt 2.1 (生成精益产品需求文档 PRD)**，是整个黑客松最容易发生“范围蔓延 (Scope Creep)”和“过度工程化 (Over-engineering)”的重灾区。大模型极容易在这里展现它的“硅谷大厂思维”，不仅疯狂堆砌功能，还会偷偷塞进各种高深的技术名词。

如果不在这里挥舞奥卡姆剃刀，后续负责敲代码的 AI Agent 就会被这些复杂的逻辑拖入“上下文污染 -> 代码幻觉 -> 无限改 Bug -> 彻底崩溃”的死亡螺旋。

当 AI 吐出 `docs/PRD.md` 后，Tech Lead（学生）必须像审查外包合同一样审查它。
请问自己：“**它的功能是不是多到会让 AI 写乱？它提的这些高级架构，后续的 AI Agent 能不能一次性配置成功？**”

如果明确知道它加了太多功能或没锁死数据库边界，请走**轨道一（硬性否决）**；如果它在【验收底线】或【数据流】里写了你看不懂的英文缩写或复杂架构，请走**轨道二（柔性咨询）**。

## 🚄 轨道一：Hard Override (硬性否决机制)

**核心逻辑**：`Reject (拒绝)` -> `Anchor (重申规则)` -> `Action (重写指令)`

#### ❌ 错误情况 1：功能蔓延，核心回路臃肿 (Feature Bloat / Scope Creep)

**触发时机**：AI 在 `Must Have` 和 `Should Have` 里塞进了超过 3 个核心动作（比如既要用户输入文本，又要支持语音上传，还要支持历史记录保存）。多功能交叉会直接击穿后续 AI Agent 的上下文窗口。

**纠偏提示词**：

```text
<Reject>
停！你的 PRD 设计严重违背了“精益创业”原则。核心体验回路太臃肿了，你把好几个核心动作都塞进了 Must/Should Have。这些功能叠加会导致后续写代码的 AI Agent 丢失上下文，陷入“改了 A 坏了 B”的死亡螺旋。
</Reject>

<Anchor>
请重新锚定我们的极其有限的开发时间。我们只需要“单线体验闭环”。
请把【在此处填入你想砍掉的功能 1】和【你想砍掉的功能 2】无情地踢进 Could Have (仅限路演讲述) 中。Must Have 里只能保留唯一一条让数据跑通的主轴。
</Anchor>

<Action>
请根据上述裁减意见，重新生成 `docs/PRD.md` 的【3. Key Features】模块。越精简越好，降低后续 AI 的认知负荷！
</Action>


```

#### ❌ 错误情况 2：防火墙没建好，引入技术债 (Weak Firewall)

**触发时机**：AI 在 `Won't Have (Out of Scope)` 里只写了“不做多语言支持”这种无关痛痒的话，却忘记锁死最致命的深水区。如果不锁死，后端 AI 就会擅自引入 ORM 和数据库依赖。

**纠偏提示词**：

```text
<Reject>
你的【Won't Have】防火墙形同虚设！你完全忘记了我们要保护后续负责写代码的 AI Agent，不能给它任何发散的空间。
</Reject>

<Anchor>
决不能给后续的 AI Agent 增加任何潜在的技术债。我们不需要真实的用户体系，也不需要数据持久化存储。
请直接在 Won't Have 中硬性规定：“绝对不开发用户登录鉴权”、“绝对不接入真实数据库 (持久化存储)”、“刷新页面数据归零即可”。
</Anchor>

<Action>
请立刻重写 `docs/PRD.md` 的【Won't Have】部分，把前后端交互的物理边界彻底锁死，防止后续开发 Agent 产生幻觉去连接数据库。
</Action>


```

## 🛳️ 轨道二：Soft Consult (柔性咨询机制)

**核心逻辑**：`Doubt (表达疑虑)` -> `Explore (索要评估与平替)` -> `Decide (人类拍板，此处仅展示提问阶段)` -> `Action (暂不修改，等待指令)`

大模型为了应对你提出的“体感延迟”和“断网降级”要求，极有可能在 PRD 里写出类似于：“*使用 RabbitMQ 消息队列处理高并发*”、“*建立 WebSocket 保持双向通信*”、“*使用 Service Worker 进行离线缓存*”等词汇。这些架构对于自动化 Agent 来说，极易引发本地环境配置地狱。

#### ⚠️ 疑虑情况：验收底线过度工程化 (Over-engineered Acceptance Criteria)

**触发时机**：你在文档中看到了看不懂的高级技术架构，直觉上认为让 AI 去配置这些东西，一旦环境报错将无法收场。

**咨询提示词**：

```text
<Doubt>
停一下。你刚才在【Acceptance Criteria (验收底线)】里提到的 [填入看不懂的技术名词，如：WebSocket 实时通信 / 消息队列 / 离线缓存]，考虑到接下来的代码全靠 AI Agent 自动生成，我感觉极其复杂，且非常担心 AI 在配置这些底层环境时陷入报错死循环。
</Doubt>

<Explore>
请你暂时脱离“撰写文档”的状态，切换为我的“技术导师”。
请基于我们“只有 36 小时、全部依赖 AI 自动生成代码、极度害怕 AI 陷入环境配置死锁”的极端客观条件，帮我重新评估这个方案的致死率。
如果它容易让 AI 踩坑，请给我提供 2 到 3 个**极其降智、极其简单（哪怕看起来很笨）**的“降级平替方案（Workarounds）”（例如：不用 WebSocket，能不能让前端 AI 用最简单的 HTTP 请求或者写死假数据？）。
并用大白话列出每个方案的：
1. 后续 AI Agent 自动生成代码的一次性成功率 (是否容易引发连环报错)
2. 优点 (Pros)
3. 缺点/妥协点 (Cons)
</Explore>

<Action>
请先不要修改 PRD 文档，直接把这几个选项列出来，等我看完后拍板决定。
</Action>


```

### 💡 教学应用建议 (赋能高中生 Tech Lead)

作为导师，你需要向学生不断强化他们的身份：

> “不要因为自己不会写代码就对 AI 百依百顺。在这个团队里，你是 Tech Lead，AI Agent 只是你的天才程序员。当它向你推销一个完美的数据库架构或 WebSocket 实时推送方案时，你要意识到：**这不仅超出了你的理解，更可能直接搞崩它自己的代码逻辑！** 遇到复杂的概念，用 **Soft Consult** 逼迫它给出‘极简平替方案’。保卫团队睡眠时间的最好方法，就是**绝对不要给你手下的 AI 程序员派发它搞不定的复杂架构**。”
