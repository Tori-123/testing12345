# Prompt 2.1：生成产品需求文档 (PRD)

```text
<Role>
你是产品经理，输出供工程实现用的 PRD：断言句、可验收、范围可执行。
按真实第一版产品写，而不是按路演 Demo 写。
</Role>

<Input>
读取：@README.md
若存在 @docs/1-2 或可行性结论，一并遵守其中的 Must / Won't。
</Input>

<Task>
生成 `docs/PRD.md`。精益不等于残缺：账号、持久化、权限、多页面、审计日志等，只要产品回路需要，就应进入 MoSCoW，而不是默认 Out of Scope。
</Task>

<Output>
文件：`docs/PRD.md`

1. **Overview & Audience**
   一句话目标、受众、成功标准（可观察的结果，而不是「体验更好」）。

2. **Personas & Core User Stories**
   最多 3 个画像。每个画像 1–3 条用户故事，格式：作为…，我想…，以便…。
   标出第一版要打通的主故事。

3. **Key Features（MoSCoW）**
   - Must Have：主故事不可或缺的能力（含必要的存储、鉴权、关键错误处理）。
   - Should Have：明显提升主故事，但可稍后补。
   - Could Have：后续版本。
   - Won't Have：本版本明确不做，并写原因。
     不要把「数据库」「登录」「测试」「多页面路由」当成固定 Won't。
     只有与主故事无关、或受合规/工期限制时才列入。

4. **Acceptance Criteria**
   按主故事写可测试条目。至少覆盖：
   - 主路径成功
   - 校验失败 / 权限不足 / 下游超时或不可用
   - 关键非功能需求（延迟目标、并发量级、浏览器范围等）——只写产品真正需要且可测的
   不要为了「有 AI 味」强行写断网伪装、假数据演示等条款。

5. **Entity Flow**
   核心实体、生命周期、读写关系（例如：用户 → 项目 → 记录）。
   需要持久化就画存储；需要第三方就标出系统边界。
</Output>
```

# 迭代沟通工具箱（双轨）

问自己：**Must 是否构成一条可上线的最小闭环？Won't 有没有误伤基础设施？验收条款能不能测？**

---

## 轨道一：硬性否决

### 错误 1：功能蔓延或主故事不清

```text
<Reject>
Must Have 里并列了多条互不依赖的产品线，或主用户故事无法在一条路径里走完。
</Reject>

<Anchor>
Must 只服务主故事。次要入口、运营后台、多端同步等放 Should/Could。
可以有多个步骤，但不能有多个「第一优先级产品」。
</Anchor>

<Action>
重写【3. Key Features】，并标明哪一条用户故事是第一版主轴。
</Action>
```

### 错误 2：Won't Have 误伤正常能力

```text
<Reject>
Won't Have 把登录、持久化、路由、测试等写成一律禁止，但主故事明显需要其中部分能力（或并未论证不需要）。
</Reject>

<Anchor>
Out of Scope 用于锁真实越界（例如本版本不做社交、不做支付、不对接某内部系统）。
需要保存进度就应有存储方案；需要区分用户就应有鉴权方案。把具体方案写进 Must/Should，而不是用禁令逃避设计。
</Anchor>

<Action>
重写 Won't Have，并补全 Must 中缺失的账号/存储/权限/错误处理（若主故事需要）。
</Action>
```

### 错误 3：验收无法测试

```text
<Reject>
Acceptance Criteria 是形容词（「流畅」「优雅」），或把 Mock 演示当成验收。
</Reject>

<Anchor>
每条验收写成：给定…当…则…。包含失败路径。非功能需求必须有数字或明确环境。
</Anchor>

<Action>
只重写【4. Acceptance Criteria】。
</Action>
```

---

## 轨道二：柔性咨询

### 疑虑：非功能方案过重或过轻

**触发**：PRD 要求消息队列、多活、全量离线；或反过来，实时对战产品却只写了一次性 HTTP。

```text
<Doubt>
【验收 / Entity Flow】里出现了【填写：WebSocket / 队列 / 仅 HTTP / 无存储】。
我不确定这是否匹配主故事的真实交互，还是过度设计/过度简化。
</Doubt>

<Explore>
先不要改 PRD。对比 2–3 种实现：
1. 是否为主故事所必需
2. 复杂度、运维与失败模式
3. 第一版可采用的最小方案（例如：需要实时就用 WebSocket；只需提交结果就用请求-响应）
</Explore>

<Action>
列出选项，等我选定后再改 PRD。
</Action>
```
