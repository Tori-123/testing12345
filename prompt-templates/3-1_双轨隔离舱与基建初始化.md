# Prompt 3.1：仓库脚手架与基建初始化

在空仓库或约定的项目根目录、Agent 模式下使用。不要在这一步写业务功能。

```text
<Role>
你是负责仓库初始化的工程师。目标是可运行、边界清楚、后续能加业务与测试的脚手架，而不是一次性搭完产品。
</Role>

<Context>
默认结构：仓库根目录下前后端分目录（monorepo-lite）。
- 前端：React + Vite + Tailwind CSS（README 另有指定则服从）
- 后端：Python + FastAPI
不要为了「怕 lint 打扰模型」而省略基础工程质量；也不要在初始化时加入用不到的 Kubernetes/多环境矩阵。
</Context>

<Input>
读取：@README.md 、 @docs/schema.md
</Input>

<Task>
不要实现 PRD 里的业务接口或 UI。只搭目录、依赖、环境模板和健康检查入口。
</Task>

<Output>
在工作区创建：

## 1. 根目录
`.cursorignore`（避免索引构建产物与密钥），至少包含：
```
node_modules/
dist/
build/
.env
__pycache__/
*.pyc
venv/
.venv/
```

`.env.example`：只放占位符，不写真实密钥。按 schema/README 列出真正会用到的变量，例如：
```
API_KEY=
DATABASE_URL=
```
不要写死某个厂商的 key 名，除非项目已指定。

根目录 `README.md` 的「本地运行」一节：补前后端安装与启动命令（若文件已存在则更新该节，不要覆盖产品定位）。

## 2. 前端 `/frontend`
- `package.json`、Vite、Tailwind 基础配置
- `src/main.jsx` 与 `src/App.jsx`：可运行的占位页（如 “Frontend is ready”），不要业务组件、不要先做完整路由系统
- 按当前 Vite 模板补齐 `index.html` 等必需文件
- 可选：基础 ESLint 配置（宽松到能配合团队即可，不要上无法通过的零容忍规则）

## 3. 后端 `/backend`
- `requirements.txt`：fastapi、uvicorn、pydantic、httpx；若 PRD 需要数据库，可列入驱动但不要连真实库、不要写业务表
- `main.py`：FastAPI 应用 + `GET /health` 返回 JSON
- 说明如何用 venv 安装并启动

不要在本步添加：业务路由、Dockerfile 集群、GitHub Actions 全套发布流——除非团队明确要求「最小 CI」（例如仅 lint/test 占位）。
</Output>
```

---

### 人类核对

1. 复制 `.env.example` 为 `.env`，人工填密钥，不要让模型把密钥写进仓库。
2. `cd frontend && npm install && npm run dev`，确认占位页。
3. 后端：创建 venv，`pip install -r requirements.txt`，`uvicorn main:app --reload`，访问 `/health`。

# 迭代沟通工具箱（双轨）

问自己：**有没有提前写业务？目录是否前后端分离？有没有塞进当前用不上的庞大工具链？**

---

## 轨道一：硬性否决

### 错误 1：脚手架里出现业务实现

```text
<Reject>
初始化阶段写了业务 UI、真实模型调用或数据库表结构。这会让后续实现在脏基线上打补丁。
</Reject>

<Anchor>
前端只保留可运行占位；后端只保留 /health。业务按 TASK_TRACKER 再做。
</Anchor>

<Action>
删掉业务代码，恢复最小可运行入口。
</Action>
```

### 错误 2：目录混杂

```text
<Reject>
前端与后端文件混在根目录，或自创了与约定不符的顶层目录（如根目录 /src 同时塞前后端）。
</Reject>

<Anchor>
前端仅在 /frontend，后端仅在 /backend，文档在 /docs。根目录只放仓库级文件。
</Anchor>

<Action>
挪到约定目录，删除建错的顶层文件夹。
</Action>
```

---

## 轨道二：柔性咨询

### 疑虑：现在是否引入 Docker / CI / 严格 lint

```text
<Doubt>
脚手架里出现了【填写：Dockerfile / CI / 严格 ESLint】。我想区分「现在有用」和「以后再加」。
</Doubt>

<Explore>
先不要删改文件。说明：
1. 当前团队是否已经需要容器或 CI
2. 最小有用版本是什么（例如仅 healthcheck 的 Dockerfile，或只跑 test 的 workflow）
3. 若推迟：把该事项记到 TASK_TRACKER 即可
不要建议「为了让模型不报错而关闭所有检查」。检查规则应与团队质量要求一致，过严再放宽，而不是零质量。
</Explore>

<Action>
只给建议，等我决定后再改仓库。
</Action>
```
