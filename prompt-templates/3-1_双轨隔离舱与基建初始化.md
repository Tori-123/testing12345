### 🛑 人类干预点 (The "Human-in-the-Loop" Checkpoint)

当 Cursor 自动创建完这一大堆文件后，需要进行以下三步“基建连通性测试”：

1. **环境克隆**：手动把根目录下的 `.env.example` 复制一份并重命名为 `.env`，填入真实的 API 密钥（这一步绝对不能让 AI 代劳，以防密钥被写死在公开文件中）。
2. **前端点火**：打开终端，输入 `cd frontend` -> `npm install` -> `npm run dev`。打开浏览器看看有没有显示 "Frontend is Ready"。如果有，成功！按下 `Ctrl+C` 关掉。
3. **后端点火**：打开终端，输入 `cd backend` -> （用 `python -m venv venv` 激活虚拟环境）`pip install -r requirements.txt` -> `uvicorn main:app --reload`。在浏览器打开 `[http://127.0.0.1:8000/health](http://127.0.0.1:8000/health)`，看看是否返回了那段 JSON。如果有，成功！

**Prompt 3.1 (双轨隔离舱与基建初始化)** 是后续所有代码生成的物理地基。在这个环节，大模型最容易犯的职业病是“过度热情（Over-scaffolding）”：它不仅会帮你建好空文件夹，还常常忍不住“顺手”帮你写几个它自认为炫酷的 UI 组件，甚至自作主张配置上 Docker、ESLint 或者 GitHub Actions。

作为 Tech Lead，你必须清醒地意识到：**初始脚手架越重，后续负责敲代码的 AI Agent 越容易被这些无关的配置文件绕晕，最终在各种 Lint 报错和环境依赖中陷入死锁。**

# 🧰 阶段三：Prompt 3.1 迭代沟通工具箱 (双轨制 Follow-up Templates)

> **Tech Lead 护栏心法**：基建的唯一目标是“纯净”。如果脚手架里混入了任何多余的业务代码，或者引入了强迫症级别的代码格式化工具（如严格的 ESLint），后续的 AI Coder 在写代码时就会因为格式不合规或上下文混乱，频繁触发无意义的报错。

当 AI 帮你生成完基建文件和目录树后，请检查左侧的资源管理器。
请问自己：“**它是不是偷偷写了具体的业务代码？它有没有建错文件夹名字？它有没有引入我没要求的配置文件？**”

如果它写了业务逻辑或搞乱了 `/frontend` 和 `/backend` 的目录结构，请走**轨道一（硬性否决）**；如果它在配置文件里塞入了你看不懂的部署或校验工具，请走**轨道二（柔性咨询）**。

## 🚄 轨道一：Hard Override (硬性否决机制)

**核心逻辑**：`Reject (拒绝)` -> `Anchor (重申规则)` -> `Action (重写指令)`

#### ❌ 错误情况 1：过度热情的业务代码 (Premature Implementation)

**触发时机**：你在 `src/App.jsx` 或 `main.py` 里不仅看到了 "Ready" 的提示，还看到了它顺手帮你写的登录界面代码、路由配置或是真实的数据库连接逻辑。

**纠偏提示词**：

```text
<Reject>
停！你过度发挥了。你在基建中混入了具体的业务逻辑和 UI 组件！这会严重污染我们初始项目的纯净度，导致后续接手的 AI Agent 丢失“白纸状态”，陷入修改既有烂代码的幻觉中。
</Reject>

<Anchor>
请严格遵守基建纪律：【绝对不要编写任何具体的业务逻辑或 UI 组件】！
前端的 App.jsx 只能有一句普通的文本 "Frontend is Ready"；后端的 main.py 只能有一个最基础的 `/health` 探针接口。不要越俎代庖！
</Anchor>

<Action>
请立刻将刚才多写的业务逻辑代码全部删除，把前后端入口文件恢复到极其克制的、只有一行返回信息的脚手架初始状态。
</Action>

```

#### ❌ 错误情况 2：物理隔离失败，目录结构混乱 (Structure Chaos)

**触发时机**：AI 没有在根目录下创建 `/frontend` 和 `/backend`，而是把前端和后端文件混在了一起；或者它自创了诸如 `/app`, `/src/server` 这种偏离我们“单体多包”设计的目录。

**纠偏提示词**：

```text
<Reject>
你完全搞乱了我们的物理隔离目录！这种混乱的文件层级，会让后续分别负责前后端的 AI Agent 找不到自己的工作区，最终导致它们互相篡改对方的代码。
</Reject>

<Anchor>
请重新锚定“单体多包 (Monorepo-lite)”原则。项目根目录下必须且只能有非常清晰的物理边界：
前端所有文件必须收纳在 `/frontend` 目录下，后端所有文件必须收纳在 `/backend` 目录下。任何跨界的文件存放都将引发灾难。
</Anchor>

<Action>
请无情地删掉刚才建错的目录，严格按照我给出的目录清单，重新构建最纯净的“双轨物理隔离”脚手架。
</Action>

```

## 🛳️ 轨道二：Soft Consult (柔性咨询机制)

**核心逻辑**：`Doubt (表达疑虑)` -> `Explore (索要评估与平替)` -> `Decide (人类拍板，此处仅展示提问阶段)` -> `Action (暂不修改，等待指令)`

大语言模型有着根深蒂固的“大厂最佳实践”潜意识。在初始化脚手架时，它经常会好心地帮你配上 Dockerfile、Kubernetes 部署脚本、或是极其严格的 ESLint/Prettier 规则。**这些工具对人类程序员是好帮手，但对 AI Agent 来说，往往是引发无尽 Lint 报错和环境挂死的元凶。**

#### ⚠️ 疑虑情况：引入了容易引发环境死锁的高级 DevOps 工具 (Over-engineered Tooling)

**触发时机**：你在生成的文件列表中看到了 `Dockerfile`, `.github/workflows/`, `.eslintrc.js`, 或者是复杂的 Webpack 配置（代替了你要求的 Vite）。

**咨询提示词**：

```text
<Doubt>
停一下。你在基建文件里加入了 [填入多余的配置文件，如：Dockerfile / 严格的 ESLint 规则 / CI/CD 脚本]。考虑到接下来的所有代码都由 AI Agent 自动生成并自动修改，我极其担心这种过于严苛的环境校验或容器化部署，会导致 AI Agent 在写代码时频繁触发格式报错，最终陷入为了修复 Lint 错误而无限兜圈子的死亡螺旋。
</Doubt>

<Explore>
请你暂时脱离“DevOps 工程师”的状态，切换为我的“技术导师”。
基于我们“只有 36 小时、纯粹靠 AI 本地生成跑通代码、极其害怕环境校验报错”的极端条件，帮我重新评估引入这些工具对 AI 协同的致死率。
如果它们容易拖垮 AI 的执行效率，请给我提供 1 到 2 个**极其降智、零校验约束**的“降级平替方案”（例如：不需要 Docker，全部本地裸机运行；或者彻底关闭 ESLint 检查）。
请用大白话列出：
1. 原方案导致后续 AI 生成代码时卡壳/报错的风险。
2. 降级方案 (如裸奔运行) 的开发顺滑度与缺点。
</Explore>

<Action>
请先不要在项目中创建这些配置文件，直接把评估选项列出来，等我看完后拍板决定。
</Action>

```
