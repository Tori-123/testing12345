# Prompt 1.3：开源资产沉淀与 README 生成 (Condense & Output)

<Role>
你现在切换身份为一名擅长科技产品包装与开源资产管理的极客。
</Role>

<Input>
读取前两轮对话中锁定的微观痛点、竞品弱点以及目标用户画像。
</Input>

<Task>
将所有研究成果收敛，转化为开发期的最高行动纲领，生成 `README.md`。
</Task>

<Output>
文件名称：`README.md`
请严格使用 Markdown 格式，必须包含以下层级：
- [ ] 顶部大标题：产品名称 (请你想一个具有极客感的英文或拼音名字)
- [ ] 标语 (Slogan)：一句简短、直击人心、带有煽动性的产品主张
- [ ] 🎯 核心痛点与问题陈述 (The Problem)
- [ ] 👥 目标用户画像 (Target Audience)
- [ ] ✨ 核心解决方案 (The Solution)：(限制在 3 条以内，强调如何利用企业提供的特定 AI 算力)
- [ ] 📚 资源与参考 (Resources & References)
</Output>





# 🧰 阶段一：Prompt 1.3 迭代沟通工具箱 (双轨制 Follow-up Templates)

> 对于 **Prompt 1.3 (开源资产沉淀与 README 生成)**，虽然它主要是一个总结性文档，但它是后续所有 Cursor AI Agent 每次对话前都会悄悄读取的“全局潜意识”。
> 如果在【核心解决方案】中塞入了听起来很高大上、但极其难写的技术架构，下游的 AI Agent 就会真的去配置这些极难的架构，直接导致项目崩盘。

作为 Tech Lead，你需要确保这份 `README.md` 既有极客的“战斗宣言”气质，又在技术承诺上保持极其克制，绝不给手下的 AI 程序员挖坑。

面对 AI 生成的 README，请问自己：“**它是文风/排版违规了，还是方案写得太深奥，会让后续的 AI Agent 陷入幻觉？**”

如果明确知道它起的名字太土、排版太密、罗列的废话功能太多，请走**轨道一（硬性否决）**；如果在核心解决方案里看到了你完全不懂的技术名词，请走**轨道二（柔性咨询）**。

## 🚄 轨道一：Hard Override (硬性否决机制)

**核心逻辑**：`Reject (拒绝)` -> `Anchor (重申规则)` -> `Action (重写指令)`

#### ❌ 错误情况 1：产品命名与 Slogan 像“企业公文” (Boring Branding)

**触发时机**：AI 给出的名字类似“智能学习助手”、“高效办公通”，Slogan 是“让你的生活更美好”、“提升您的工作效率”这种极其乏味、毫无攻击性的废话。

**纠偏提示词**：

```text
<Reject>
你起的产品名称和 Slogan 太无聊、太有“企业公文感”了！这根本不像是一个要在黑客松上拿大奖的极客项目。
</Reject>

<Anchor>
请重新思考品牌包装。产品名称需要简短、犀利，最好带一点赛博朋克或极客幽默感（可以使用合成词或带后缀的拼音）。
Slogan 必须“带有煽动性”，直接把尖刀插进用户的痛点里，不要用“提升效率”、“美好生活”这种陈词滥调。
</Anchor>

<Action>
请保持文档其他部分不变，重新为我提供 3 组【产品名称 + 标语 (Slogan)】的绝佳搭配供我挑选。语言要具有极强的视觉冲击力！
</Action>


```

#### ❌ 错误情况 2：核心解决方案发散，忘记了 AI 的主角地位 (Solution Bloat & AI Missing)

**触发时机**：AI 在【核心解决方案】里列出了 4、5 条常规的软件功能（比如“友好的 UI 界面”、“历史记录保存”），而把大模型的特定能力一笔带过。

**纠偏提示词**：

```text
<Reject>
你的【核心解决方案】偏题了，罗列了太多常规功能。如果我们把这些写进 README，下游负责敲代码的 AI Agent 就会“迷失重点”，浪费大量算力去写普通的增删改查页面，而不是聚焦打磨核心的大模型交互。
</Reject>

<Anchor>
请立刻回想我们只有 36 小时，且所有代码由 AI 自动生成。我们必须极大程度地降低下游 Agent 的认知负荷！
我曾严格要求解决方案【限制在 3 条以内】，并且必须【强调如何利用企业提供的特定 AI 算力】。
</Anchor>

<Action>
请大幅删减并重写【✨ 核心解决方案 (The Solution)】部分。只保留 1-2 个最具毁灭性打击能力的 Feature，并且在每一条中，用加粗字体明确写出：“这里利用了 [大模型名称] 的 [某项具体能力] 来实现...”。
</Action>


```

#### ❌ 错误情况 3：排版密集，不像 GitHub 源码文档 (Poor Readability)

**触发时机**：AI 输出的文档全是密密麻麻的大段文字，没有合理的加粗、没有留白，缺乏开源项目的“门面感”。

**纠偏提示词**：

```text
<Reject>
这份 README 的排版太密集了，像是一篇毫无感情的论文，让人完全没有阅读的欲望。
</Reject>

<Anchor>
作为一份极客的源码文档（README.md），它必须具备极高的“可扫视性（Scannability）”。
对于痛点和画像描述，能用无序列表（Bullet points）的就不要用长句；重要的痛点关键词、情绪词必须加粗高亮。
</Anchor>

<Action>
请在不改变原意的前提下，重新进行 Markdown 格式的视觉排版。大量增加换行、列表、加粗以及相关的 Emoji 符号，让这份文档充满力量感和呼吸感。
</Action>


```

## 🛳️ 轨道二：Soft Consult (柔性咨询机制)

**核心逻辑**：`Doubt (表达疑虑)` -> `Explore (索要评估与平替)` -> `Decide (人类拍板，此处仅展示提问阶段)` -> `Action (暂不修改，等待指令)`

有时，大模型为了让 README 看起来很专业，会在【核心解决方案】里写上：“*基于 RAG (检索增强生成) 技术搭建专属知识库*” 或 “*引入向量数据库 (Vector DB) 进行语义匹配*”。如果学生顺着它写进 README，后面的代码 Agent 就会真的去引入庞大的数据库依赖，直接把环境跑崩。

#### ⚠️ 疑虑情况：解决方案包含极易让 AI 翻车的高级架构 (Over-engineered Architecture)

**触发时机**：你在文档中看到了你不懂的技术缩写（如 RAG、Vector DB、Fine-tuning、消息队列等）。

**咨询提示词**：

```text
<Doubt>
停一下。你在【核心解决方案】中提到了 [填写让你疑虑的技术名词，如：RAG 向量数据库 / 知识库微调]。考虑到后续我们是让 Cursor AI Agent 全自动写代码，我非常担心把这个词写进 README 后，下游的 AI 会自作主张去引入复杂的依赖库，最终陷入环境报错的死亡螺旋。
</Doubt>

<Explore>
请你暂时脱离“撰写文档”的状态，切换为我的“技术导师”。
基于我们“只有 36 小时、全靠 AI 自动生成代码、越简单越好”的极端条件，帮我重新评估这个技术名词对 AI Agent 的“致死率”。
如果它极易引发连环报错，请给我提供 2 个**极其降智、极其简单**的“降级平替方案”（例如：不需要外接向量数据库，能不能直接把少量资料硬编码塞进 Prompt 里？）。
请用大白话列出：
1. 原方案被 AI 自动生成时的翻车风险。
2. 降级方案 A、B 的开发稳健度与视觉妥协点。
</Explore>

<Action>
请先不要修改 README 文档，直接把这几个选项列出来，等我看完并拍板决定后，我们再把最终决定写进 README。
</Action>


```
