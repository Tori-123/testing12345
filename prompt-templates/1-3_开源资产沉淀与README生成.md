# Prompt 1.3：产品定位沉淀与 README 生成

```text
<Role>
你负责把调研收敛成一份后续开发会反复阅读的产品说明（README）。文风清楚、可扫视，技术承诺克制。
</Role>

<Input>
使用前两轮已锁定的内容：
- 场景名称与痛点
- 竞品缺口
- 目标用户
- Must / Won't
- 关键依赖与开放问题

若对话中没有完整材料，先列出缺口再写，不要编造。
</Input>

<Task>
生成 `README.md`。这是产品定位与协作入口，不是架构设计书。
不要在 README 里写死尚未评估的技术选型（向量库、微服务、特定云厂商等），除非 1.2 已经确认。
</Task>

<Output>
文件：`README.md`

必须包含：

# 产品名称
（简洁、可发音、避免「智能 XX 助手」套话。给出 1 个主推荐 + 2 个备选。）

## 一句话定位
说明给谁、解决哪一件事。不要空泛口号。

## 问题
用列表写清痛点与现有方案缺口。

## 用户
用 1.2 的画像压缩成一段 + 若干要点。

## 解决方案（第一版）
不超过 5 条。每条对应核心回路中的一步，而不是愿望清单。
若使用模型/检索/第三方 API，写清它承担哪一步，以及没有它时产品是否仍成立。

## 范围
- 第一版包含
- 明确不做（与 1.2 Won't 对齐）

## 技术与依赖（已知部分）
只写已确定的栈和必须接入的系统。未定项放「开放问题」。

## 本地运行（可暂留占位）
后续脚手架完成后再补命令。此处可写「待 3.1 初始化后补充」。

## 参考
链接、竞品、数据源、规范文档。
</Output>
```

---

# 迭代沟通工具箱（双轨）

README 会被后续对话当作默认上下文。问自己：**定位是否清楚？有没有提前承诺做不到或没必要的架构？**

---

## 轨道一：硬性否决

### 错误 1：命名与定位像套话

```text
<Reject>
名称和一句话定位无法让人知道这是给谁、解决哪件事。
</Reject>

<Anchor>
名称简短即可，不必强行「极客」或「赛博」。定位句必须包含用户 + 场景 + 结果。
禁止「让生活更美好」「提升效率」这类无法验收的句子。
</Anchor>

<Action>
其他章节不动，给出 3 组【名称 + 一句话定位】供选择。
</Action>
```

### 错误 2：解决方案变成功能清单或技术秀

```text
<Reject>
解决方案罗列了界面、历史记录、社区等常规项，或堆砌了 RAG/中台等尚未评估的架构，核心回路反而看不清。
</Reject>

<Anchor>
每条解决方案都应对应「用户原来卡在哪，现在怎么完成」。
技术名词只能出现在它真正负载的那一步，并与 1.2 的 Must 一致。
</Anchor>

<Action>
重写【解决方案】和【范围】，与 1.2 对齐，删掉未评估的架构承诺。
</Action>
```

### 错误 3：排版无法扫视

```text
<Reject>
README 大段叙述，关键边界（做什么/不做什么）不容易被扫到。
</Reject>

<Anchor>
痛点、范围、依赖用列表。关键词加粗。少用装饰性 emoji，需要时只用在标题层级。
</Anchor>

<Action>
不改含义，只重排 Markdown，让范围和依赖在 30 秒内能读完。
</Action>
```

---

## 轨道二：柔性咨询

### 疑虑：README 写进了未评估的架构

**触发**：RAG、向量库、微调、消息队列、多区域部署等出现在解决方案里，但 1.2 并未确认。

```text
<Doubt>
【解决方案】里出现了【填写技术名词】。1.2 没有把它列为已确认依赖。我担心后续实现会按 README 去搭整套基础设施。
</Doubt>

<Explore>
先不要改 README。说明：
1. 该能力是否为第一版闭环所必需。
2. 若必需：最小实现路径（含托管服务 vs 自建）。
3. 若非必需：README 应如何改写，避免被当成已定架构。
</Explore>

<Action>
只给建议，等我选定后再改 README。
</Action>
```
