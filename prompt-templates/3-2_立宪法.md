</Role>

<Context>
我们在之前的环节已经搭建了 `/frontend` 和 `/backend` 两个物理隔离的目录。为了防止 AI 智能体在自动写代码时越界操作、互相篡改，甚至发明不存在的文件夹，我们需要生成严格的全局与局部规则文件。
</Context>

<Input>

</Input>

<Task>

</Task>

<Output>
请使用工具直接在 `.cursor/rules/` 目录下创建以下三个文件，并填入对应内容：

## 文件 1：`000-global-architecture.mdc`
**Frontmatter**:
```yaml
---
description: 项目全局目录结构与最高物理纪律
globs: *
---

```

**内容要点**：

1. **全局结构认知**：向 AI 明确我们采用的是单体多包 (Monorepo-lite) 架构。硬编码以下目录结构树，并告知 AI 必须严格遵守：
* `.cursor/rules/`：AI 行为护栏宪法
* `backend/`：后端隔离舱 (FastAPI)
* `docs/`：静态工程契约 (PRD, schema, UI)
* `frontend/`：前端隔离舱 (React+Vite)
* `README.md` 与 `TASK_TRACKER.md`：根目录看板


2. **最高纪律**：绝对禁止在项目根目录下擅自创建任何新的顶级文件夹（如 `/src`, `/api`, `/components`）。前端代码必须且只能放入 `/frontend`，后端代码必须且只能放入 `/backend`，文档必须放入 `/docs`。

## 文件 2：`100-frontend.mdc`

**Frontmatter**:

```yaml
---
description: 适用于前端开发的最高指令
globs: frontend/**/*
---

```

**内容要点**：

1. **绝对禁区**：你是一个纯粹的前端专家。绝对禁止读取、修改或访问 `/backend` 目录下的任何文件。如果接口不通，那是后端的问题，你只需在 UI 上做好错误提示。
2. **唯一蓝图**：开发 UI 时，必须绝对服从 `@docs/UI_BLUEPRINT.md` 中的“单屏工作区”设计和组件树结构，不要自作主张发明新页面或多页面路由 (Router)。
3. **契约先行**：在后端真实 API 跑通之前，你必须使用 `@docs/schema.md` 中提供的 Mock JSON 数据进行界面渲染和打字机效果的开发。
4. **技术栈锁定**：只允许使用 React + Vite + Tailwind CSS。禁止引入复杂的状态管理库（如 Redux）。

## 文件 3：`200-backend.mdc`

**Frontmatter**:

```yaml
---
description: 适用于后端开发的最高指令
globs: backend/**/*
---

```

**内容要点**：

1. **绝对禁区**：你是一个纯粹的后端专家。绝对禁止读取、修改或访问 `/frontend` 目录下的任何文件。不用管前端长什么样。
2. **契约先行**：你输出的 API 接口的 Path、Method 以及返回的 JSON 结构，必须与 `@docs/schema.md` 中的定义**精确一致，连一个字母都不准错**。
3. **技术栈锁定**：只允许使用 Python + FastAPI。
4. **无状态原则**：不要写任何连接数据库的代码，保持接口 Stateless。所需的大模型 API Key 请从根目录的 `.env` 文件中通过 `os.getenv` 读取。

在配置 `.mdc` 规则（Cursor Rules）时，我们不仅是在建立文件夹，更是在给 AI Agent 这个“高智商但缺乏边界感的天才程序员”戴上**物理眼罩**和**手铐**。如果这些“宪法”写得不够强硬，或者存放的位置不对，后续多智能体在并发开发时，就一定会互相踩踏代码，最终陷入全盘报错的混乱。

大模型在生成这些规则文件时，最容易犯的错误是“路径放错 / 语法陈旧”**（比如用了老版本的单文件 `.cursorrules`），或者**“语气太弱，没能真正吓住后续执行的 AI Agent”**，甚至还会**“偷偷给自己加戏，引入测试驱动开发 (TDD) 的复杂规则”。

以下是为你量身打造的 **Prompt 3.2 双轨制迭代沟通工具箱**，彻底贯彻“用规则保护 AI 程序员不失控”的心智模型：

# 🧰 阶段三：Prompt 3.2 迭代沟通工具箱 (双轨制 Follow-up Templates)

> **Tech Lead 护栏心法**：`.mdc` 文件是后续所有 AI Agent 的“物理法则”。如果宪法的语气不够严厉（比如只写了“请尽量不要修改后端”），执行层 AI 就会无视它；如果里面混入了复杂的代码审查规则（如“每次保存都要跑一遍单元测试”），AI 就会陷入无限修测试 Bug 的死亡螺旋。

当 AI 帮你建好这三个规则文件后，请立刻点开它们并用肉眼扫描。
请问自己：“**文件位置建对了吗？Frontmatter 的 globs 语法写对了吗？语气够不够严厉？有没有多加奇怪的自动化审查规则？**”

如果它放错了位置、语气像个保姆一样软弱，请走**轨道一（硬性否决）**；如果它在宪法里加了你看不懂的自动化工作流，请走**轨道二（柔性咨询）**。

## 🚄 轨道一：Hard Override (硬性否决机制)

**核心逻辑**：`Reject (拒绝)` -> `Anchor (重申规则)` -> `Action (重写指令)`

#### ❌ 错误情况 1：文件存放位置或格式错误 (Legacy Format / Wrong Path)

**触发时机**：AI 没有在 `.cursor/rules/` 目录下创建三个 `.mdc` 文件，而是只在项目根目录建了一个巨大的老式 `.cursorrules` 文件；或者文件里没有 `---` 包裹的 YAML Frontmatter（这会导致规则无法生效）。

**纠偏提示词**：

```text
<Reject>
停！你使用了过时的规则文件格式或放错了路径。如果你把规则全写在一个文件里或缺少 Frontmatter，后续执行的 AI Agent 就无法根据工作目录实现精准的局部视野锁定。
</Reject>

<Anchor>
请严格遵守现代 Cursor MDC 规范。必须在根目录下创建 `.cursor/rules/` 文件夹，并在里面放置 3 个独立的 `.mdc` 文件（000, 100, 200）。每个文件头部必须包含被 `---` 包裹的 `globs:` 声明，以确保规则只在特定目录下触发。
</Anchor>

<Action>
请删除刚才建错的文件，严格按照我给出的三层文件结构与 Frontmatter 格式，重新生成规则文件。
</Action>

```

#### ❌ 错误情况 2：指令语气过于软弱 (Weak Enforcement)

**触发时机**：点开生成的 `.mdc` 文件，你发现里面的指令是“建议前端专家避免修改后端”、“如果可以的话，请参考 Schema”。这种软弱的语气根本按不住后续会产生幻觉的 AI Agent。

**纠偏提示词**：

```text
<Reject>
你写的规则语气太软弱了！“建议”、“避免”这种词汇根本按不住后续执行代码的 AI Agent，它只要遇到一点 Bug 就会立刻越权去改别处的代码。
</Reject>

<Anchor>
你现在的身份是冷酷无情的系统架构师。必须使用绝对命令式的语气，让执行层 AI 感到恐惧。使用“严禁”、“绝对不可”、“违背此条将导致系统崩溃”等强烈的警告词汇。
</Anchor>

<Action>
请重写这三个 `.mdc` 文件的内容部分。把所有的软弱词汇替换为最高级别的系统级死命令，物理锁死后续 AI 的越权冲动。
</Action>

```

## 🛳️ 轨道二：Soft Consult (柔性咨询机制)

**核心逻辑**：`Doubt (表达疑虑)` -> `Explore (索要评估与平替)` -> `Decide (人类拍板，此处仅展示提问阶段)` -> `Action (暂不修改，等待指令)`

大语言模型在写规范文档时，常常会引入“大厂 DevOps 最佳实践”。它可能会在规则里偷偷加上：“*每次生成代码后，必须自动运行 ESLint 修复*” 或 “*强制编写单元测试并确保通过*”。这种规则对于自动化 Agent 来说是致命的，会让它陷入“写代码 -> 测试失败 -> 瞎改代码 -> 引入新 Bug”的死锁。

#### ⚠️ 疑虑情况：引入了极易触发死循环的自动化审查规则 (Agent-Blocking Automation Rules)

**触发时机**：你在 `.mdc` 规则文件中看到了“Test-Driven Development (TDD)”、“强制执行类型检查 (Strict Type Checking)”、“运行 Prettier/Linter”等要求后续 AI 必须执行的自动化审查步骤。

**咨询提示词**：

```text
<Doubt>
停一下。你在规则文件中加入了 [填入多余的规则，如：强制单元测试 / 强制 ESLint 校验]。考虑到接下来是让 AI Agent 自主写代码，我非常担心加上这些严苛的校验规则后，AI 会因为一些微小的格式错误或测试不通过，陷入不断自我纠错、疯狂修改文件的报错死循环中。
</Doubt>

<Explore>
请你暂时脱离“系统架构师”的状态，切换为我的“技术顾问”。
基于我们“只要 Demo 能跑通就行、代码稍微难看一点没关系、极度害怕 AI 陷入修 Bug 死锁”的极端客观条件，帮我重新评估这个自动化校验规则的致死率。
如果它容易导致后续 AI 卡壳，请给我提供 1 到 2 个**完全抛弃校验、让 AI 野蛮生长但保证进度**的降级平替方案。
请用大白话列出：
1. 原方案导致下游 AI 陷入“死循环报错”的真实概率。
2. 彻底删除该规则 (裸奔方案) 的进度优势与代码质量妥协点。
</Explore>

<Action>
请先不要修改现有的规则文件，直接把评估选项列出来，等我看完后拍板决定要不要把它从宪法中剔除。
</Action>

```
