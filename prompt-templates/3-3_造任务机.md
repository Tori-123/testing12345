# Prompt 3.3：生成任务拆分（Task Tracker）

在仓库级对话中使用。任务要细到文件、路由、组件，并包含测试与联调，而不是只服务当场演示。

```text
<Role>
你负责把已定契约拆成可执行的工程任务清单。
</Role>

<Context>
按真实交付拆分：实现、联调、测试、错误处理。工期按 README/PRD 中的约束估算，不要写「36 小时看板」或「卡死一小时就砍成假数据」。
</Context>

<Input>
读取：
- @docs/PRD.md
- @docs/schema.md
- @docs/UI_BLUEPRINT.md
</Input>

<Task>
生成根目录 `TASK_TRACKER.md`。任务必须具体，例如：「在 backend/main.py 增加 POST /api/v1/…，校验 Request Schema 字段 X」。
禁止写入 PRD Won't Have 中的事项。PRD 需要的存储、鉴权、路由、测试应出现在清单中。
</Task>

<Output>
文件：`TASK_TRACKER.md`

# 任务看板

## 后端
环境变量读取、健康检查已有则勾掉。按 schema 逐个接口：模型、路由、校验、错误码、与外部服务/数据库的接入（若需要）。每项可测。

## 前端
按 UI 蓝图逐页/逐组件。Mock 阶段与真实 API 阶段分开写：先用 Mock 搭界面，再切换 fetch/WebSocket 等真实调用。含空态、加载、错误。

## 联调
CORS、鉴权 cookie/token、环境变量、端对端主路径。Mock 替换为真实接口后，删除或隔离仅用于开发的假数据路径。

## 验收
对照 PRD Acceptance Criteria 逐条。含失败路径。自动化测试写清范围（例如 API 契约测试、关键纯函数）；不要把「禁止测试」写成纪律，也不要第一周就要求全量 E2E 平台。

文末用几条「进行中约定」即可，例如：范围变更先改 PRD/Schema；同一任务连续失败则缩小范围或人工排查，而不是用静态假界面冒充已完成。
</Output>
```

# 迭代沟通工具箱（双轨）

问自己：**任务是否可直接派给实现？有没有把 Won't Have 又写回来？测试与错误路径是否缺失？**

---

## 轨道一：硬性否决

### 错误 1：颗粒度太粗

```text
<Reject>
任务停留在「做后端」「做分析页」，无法执行、也无法验收。
</Reject>

<Anchor>
后端落到 path + 字段；前端落到蓝图中的组件名与绑定字段。
</Anchor>

<Action>
把每条粗任务拆成若干可勾选子任务，重写 TASK_TRACKER.md。
</Action>
```

### 错误 2：与 PRD 冲突

```text
<Reject>
清单出现了 Won't Have 项，或漏掉了 Must Have（含鉴权、持久化、错误处理）。
</Reject>

<Anchor>
以 PRD MoSCoW 为边界。需要的基础设施写成任务，不需要的不要借「完善架构」塞回来。
</Anchor>

<Action>
按 PRD 增删任务后重出看板。
</Action>
```

---

## 轨道二：柔性咨询

### 疑虑：测试策略过重或过空

```text
<Doubt>
看板上出现了【填写：全量 Cypress / 完全无测试】。我想确认与当前阶段匹配的最小测试集。
</Doubt>

<Explore>
先不改看板。建议：
1. 现在值得自动化的部分（契约、领域逻辑）
2. 仍适合手工验收的部分
3. 明确不在本阶段搭建的测试基础设施
</Explore>

<Action>
给出测试任务草案，等我选定后再写入看板。
</Action>
```
