# AI 辅助开发：提示词与核心资产目录

本目录用于把「需求发现 → 系统设计 → 工程基建 → 开发实现」拆成可复用的提示词。每个环节都有明确输入、输出和人类拍板点。不要把调研闲聊留在写代码的对话里，以免污染上下文。

---

## 阶段一：需求发现与研究

**核心目标**：在带联网能力的对话环境中做市场与用户研究，收敛出可开发的产品定位。阶段一适合在浏览器端完成（深度搜索、竞品抓取），不要在 IDE 里做长篇调研。

### Prompt 1.1：命题发散

- **目的**：把笼统命题拆成多个可区分的切角，只展开「可以往哪理解」，不做痛点、竞品和可行性。
- **输入**：原始命题；可选约束（目标用户、明确不做的方向），仅用于避免跑题。
- **输出**：5–8 个切角（名称、命题解读、面向谁、产品形态一句话）。
- **人类干预**：讨论后选定 **1 个** 切角进入 1.2。

### Prompt 1.2：市场调研与方案可行性验证

- **目的**：对选定切角做痛点、竞品、可行性与用户定位，锁死第一版范围。
- **输入**：1.1 中选定的切角名称与命题解读。
- **输出**：
  - 行业背景摘要
  - 竞品分析（真实产品、操作链路、缺口）
  - 可行性（第一版必须做 / 明确不做 / 核心体验回路）
  - 具象的目标用户画像
- **人类干预**：确认核心回路可实现，且「不做清单」覆盖真实风险（合规、数据源、工期），而不是一律砍掉正常工程能力。

### Prompt 1.3：产品定位沉淀与 README 生成

- **目的**：把调研收敛成后续开发可读的产品说明。
- **输入**：1.1 选定切角 + 1.2 分析报告。
- **输出**：`README.md`（产品名称、一句话定位、问题、用户、解决方案、技术栈与参考资料）。
- **人类干预**：检查解决方案是否过度承诺架构（未评估就写死 RAG、微服务、实时推送等）。

## 阶段二：系统设计

**核心目标**：把产品构想写成机器可读的工程契约。信息架构、数据持久化、鉴权、多页面路由等，按产品真实需要设计，不要为了「快出 Demo」预先禁止。

### Prompt 2.1：生成产品需求文档 (PRD)

- **目的**：明确做什么、先做什么、明确不做什么。
- **输入**：`@README.md`
- **输出**：`docs/PRD.md`
  - Overview & Audience
  - Personas & Core User Stories
  - Key Features（MoSCoW）
  - Acceptance Criteria（功能、质量、错误处理、关键非功能需求）
  - Entity Flow（实体与数据流向）
- **人类干预**：审查 Must Have 是否可在当前工期交付；Won't Have 应锁真实越界项，而不是禁止数据库、登录、测试等常规能力。

### Prompt 2.2：生成前后端数据契约与 Mock 数据

- **目的**：契约先行，让前后端可以并行。需要持久化或鉴权时，Schema 里应出现对应字段（id、时间戳、token 等）。
- **输入**：`@docs/PRD.md`
- **输出**：`docs/schema.md`
  - API 路由（Endpoint、Method、鉴权要求）
  - Request / Response Schema
  - 错误码与边界情况
  - 可用于前端开发的 Mock JSON
- **人类干预**：结构是否与 PRD 一致；嵌套是否必要；Mock 是否覆盖空态、错误态，而不只是理想成功态。

### Prompt 2.3A：UI 风格推演与提案

- **目的**：给出 2–3 种符合产品与用户的视觉方向，供团队选择。
- **输入**：`@docs/PRD.md`、`@docs/schema.md`
- **输出**：2–3 个视觉风格提案（基调、布局/信息架构、与用户匹配度）。
- **人类干预**：选定 1 款风格。布局按产品需要可以是单页工作区，也可以是多路由、导航、设置页。

### Prompt 2.3B：生成语义化 UI 蓝图

- **目的**：用组件树和状态流转替代模糊草图，降低前端生成时的结构幻觉。
- **输入**：选定风格 + `@docs/schema.md`
- **输出**：`docs/UI_BLUEPRINT.md`
  - 信息架构（页面/路由或单页分区）
  - 设计规范
  - 关键状态（空态、加载、成功、错误、权限不足等）
  - 绑定了 Schema 字段的组件树
- **人类干预**：字段是否都在 Schema 中存在；导航/路由是否与 PRD 一致；缺了哪些必要状态。

## 阶段三：工程基建

**核心目标**：搭好可维护的仓库结构、约定和任务拆分。前后端分离是为了边界清晰，不是禁止联调或全栈修改。

### Prompt 3.1：仓库脚手架与基建初始化

- **目的**：生成前后端目录、环境变量模板、基础可运行入口。
- **输入**：`@README.md`、`@docs/schema.md`
- **输出**：
  - 根目录：`.cursorignore`、`.env.example`
  - 前端：React + Vite + Tailwind（或项目指定栈）
  - 后端：FastAPI（或项目指定栈）
  - 按需：lint、测试骨架、基础 CI（不要为了「怕 AI 报错」而禁止）
- **人类干预**：配置真实 `.env`（不要让 AI 写入密钥）；前后端分别跑通健康检查。

### Prompt 3.2：生成 Cursor 规则 (`.mdc`)

- **目的**：锁定目录约定、技术栈和契约来源，减少乱建文件夹和擅自换栈。
- **输入**：`@docs/PRD.md`、`@docs/schema.md`、`@docs/UI_BLUEPRINT.md`
- **输出**：`.cursor/rules/`
  - `000-global-architecture.mdc`（目录与跨层约定）
  - `100-frontend.mdc`（前端栈、UI 蓝图、Mock 并行开发）
  - `200-backend.mdc`（后端栈、Schema 对齐、数据与鉴权按 PRD）
- **人类干预**：抽查规则是否过时、过宽或过死（例如禁止测试、禁止数据库、禁止路由）。

### Prompt 3.3：生成任务拆分 (Task Tracker)

- **目的**：把契约拆成可执行、可勾选的任务，含测试与联调，而不是只追「演示能点」。
- **输入**：`@docs/PRD.md`、`@docs/schema.md`、`@docs/UI_BLUEPRINT.md`
- **输出**：根目录 `TASK_TRACKER.md`（后端、前端、联调、验收；任务要落到文件/路由/组件级）。
- **人类干预**：删掉与 PRD `Won't Have` 冲突的项；补上测试、错误处理和必要的持久化/鉴权任务。

## 阶段四：开发实现

### Prompt 4.1：原子开发指令

- **目的**：按任务卡开发，指令指向具体文件、字段和验收方式。
- **输入**：当前任务 + 对应契约文档。
- **输出**：可运行、符合契约的代码；卡住时回滚或缩小范围，而不是用假数据冒充已联调。
- **人类干预**：功能验收、回归相关页面；范围变化先改 PRD/Schema，再改代码。
