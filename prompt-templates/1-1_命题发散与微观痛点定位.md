# 阶段一在浏览器中进行，而不是在 IDE 里

1.1 只做命题发散：把笼统命题拆成多个可区分的切角，不做痛点深挖、竞品和可行性（那些交给 1.2）。

放在 Cursor 里做长篇发散会占满写代码的上下文。用带联网/深度搜索的模型做阶段一，再用 IDE 里的模型做架构和实现。选定切角并完成 1.2 / 1.3 后，再把结论放进仓库。

---

# Prompt 1.1：命题发散

```text
<Role>
你负责命题发散：把一句笼统命题拆成多个彼此不同的解读切角，供团队挑选。
这一步只展开「可以往哪几个方向理解」，不要做痛点分析、竞品对比、MVP 裁剪或技术可行性论证。
</Role>

<Context & Constraints>
原始命题是：
【在此粘贴命题 / 业务目标】

已知约束（没有的项写「暂无」；仅用于避免明显跑题，不要据此写范围清单）：
- 目标用户或客户：
- 明确不做的方向：
</Context & Constraints>

<Task>
不要给宏大叙事，也不要写成完整产品方案。
请从原命题出发，给出 5–8 个垂直、具体、彼此可区分的切角。
每个切角必须能回答：在这个解读下，命题被收成了哪一件更小的事、面向谁、产品大概长什么样。
切角之间应换「谁 / 场景 / 产品形态」中至少一项，避免同一句话换皮重复。
</Task>

<Output>
用 Markdown 输出。每个切角用二级标题：`## 切角N：一句话名称`

每个切角只包含：

- **命题解读**：原命题在这个切角下被收成哪一句更具体的话（不写痛点成因、不写竞品为什么不行）。
- **面向谁**：一句话点出对象和使用情境。
- **产品形态**：一句话描述会做出什么（工具 / 工作流 / 平台中的哪一种），不是功能列表。
</Output>
```

选定后进入 1.2 时，粘贴：**切角名称 + 命题解读**。痛点、竞品与可行性在 1.2 再做。

# 迭代沟通工具箱（双轨）

先问自己：**这些切角是否真的在拆命题？有没有提前写成调研报告或方案书？**

- 切角空泛、雷同、或跑去写分析 → **轨道一**
- 某个切角是否还算原命题的解读 → **轨道二**

核心逻辑：

- 轨道一：`Reject` → `Anchor` → `Action`
- 轨道二：`Doubt` → `Explore` → `Action`（先评估，等你拍板再改原文）

---

## 轨道一：硬性否决

### 错误 1：切角太空或彼此雷同

**触发**：全是「帮助企业数字化」「提升体验」；或 5–8 条只换了形容词，对象和形态一样。

```text
<Reject>
这些切角过于宏大，或彼此无法区分，不能算命题发散。
</Reject>

<Anchor>
每个切角必须换掉「谁 / 使用情境 / 产品形态」中至少一项。
名称要具体到能单独拿去调研，而不是同一句口号的变体。
</Anchor>

<Action>
抛弃刚才的列表，保持原输出格式（命题解读 / 面向谁 / 产品形态），重新给出 5–8 个可区分的切角。
</Action>
```

### 错误 2：写成了痛点分析或方案书

**触发**：出现「痛点界定」「现有方案缺口」「Must/Won't」「技术依赖」「为什么传统方案失效」等 1.2 才该有的内容。

```text
<Reject>
你在做痛点分析或可行性裁剪。1.1 只发散命题切角，不分析、不裁 MVP。
</Reject>

<Anchor>
每个切角只保留三块：命题解读、面向谁、产品形态。
不要写竞品、数据从哪来、第一版做什么/不做什么。
</Anchor>

<Action>
删掉分析性段落，按原格式只输出切角列表。
</Action>
```

---

## 轨道二：柔性咨询

### 疑虑：某个切角是否已经跑题

**触发**：切角看起来有趣，但你不确定它还算不算原命题的一种解读（例如原命题是「训练工具」，切角变成了「社交社区」）。

```text
<Doubt>
切角【填写序号】把命题解读成了【填写你看到的方向】。我不确定这是否还在原命题范围内。
</Doubt>

<Explore>
先不要改列表。只评估这一条：
1. 它与原命题的关系（收窄 / 延伸 / 跑题）。
2. 若算延伸：怎样改「命题解读」才能仍连回原命题。
3. 若算跑题：用同一编号给一个仍在命题内的替代切角（先列出来，等我选再替换全文）。
</Explore>

<Action>
先只输出评估和替代建议，不要重写整份列表。
</Action>
```
